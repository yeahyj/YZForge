## 2. 面板：选择对象，预览结果，再执行

主要入口收敛为“模块与文件”“预制体与绑定”“配置表”“构建配置”；检查报告和回收记录提供辅助入口。移除人工登记动态资源的独立页面。

左侧显示模块与所属对象树；右侧根据当前操作显示必要选项；创建区域持续显示产物预览。正常操作不暴露 UUID、类注册名、生成目录和 JSON 文本。

| 需要的信息               | 交互规则                                   |
| ------------------------ | ------------------------------------------ |
| 所属模块                 | 当前选中项默认带入；可搜索下拉选择         |
| 所属资源包               | 仅列出所选模块中的包；只有一个时自动选中   |
| 模块依赖                 | 多选已有模块；不可选项显示自依赖/环路原因  |
| 新对象名字               | 输入语义名称；工具推导标识、类名和文件名   |
| Prefab、脚本、源工作簿   | 从项目对象列表或文件选择器选取             |
| Sheet、主键、索引字段    | 读取源工作簿后选择；不能引用不存在的字段   |
| 音量、日历规则、绑定前缀 | 数值控件、下拉框和可编辑表格               |
| 删除、恢复               | 选择真实对象或带名称、时间、状态的回收记录 |

后端与面板共用校验和操作计划。预览列出本操作控制的全部源文件、声明与生成文件的新增、修改、移动、回收和冲突，包括生成 TS、相关清单及由 Creator 管理的 meta；不将 library/temp 等引擎缓存宣称为可预知产物。实际执行重新检查计划涉及的文件版本；状态改变时刷新预览并保留用户未提交的输入，不能执行过期计划。

创建完成应直接定位产物，并给出可执行的下一步，例如“打开预制体”“编辑脚本”“重新绑定”。错误显示具体对象、原因与定位入口，原始堆栈收在详情中。

## 3. 命名与创建文件预览

后缀表达对象职责。界面的语义类型与实际挂载层、排序值分开：移动渲染层不应强迫改类名和 Prefab 名。

| 选择的类型     | 语义名示例 | 自动文件名                                         |
| -------------- | ---------- | -------------------------------------------------- |
| 页面           | Inventory  | InventoryPage.prefab、InventoryPage.ts             |
| 弹窗           | Reward     | RewardPopup.prefab、RewardPopup.ts                 |
| 覆盖层         | Guide      | GuideOverlay.prefab、GuideOverlay.ts               |
| 提示           | Message    | MessageToast.prefab、MessageToast.ts               |
| 加载界面       | Scene      | SceneLoading.prefab、SceneLoading.ts               |
| 可复用 UI 组件 | Item       | ItemPart.prefab、ItemPart.ts                       |
| 普通游戏预制体 | Coin       | CoinPrefab.prefab；需要脚本时生成 CoinComponent.ts |
| 独立节点组件   | Health     | HealthComponent.ts                                 |
| 普通业务服务   | Inventory  | InventoryService.ts                                |

可复用 UI 部件使用 Part 后缀，避免与 Cocos 的 Widget 布局组件重名。

统一命名函数处理大小写、分隔符、合法标识、保留名和已存在后缀，避免 RewardPopupPopup。重名检查覆盖文件系统、TypeScript 标识、`@ccclass` 注册名和逻辑 ID；同模块不同角色可以使用相同语义名。已有文件不自动追加数字或覆盖。

角色同时参与新对象的逻辑 ID，例如 Reward 的页面与弹窗分别为 reward-page、reward-popup；不能只区分文件名，却仍向 views 写入同一个 reward 键。跨模块类注册名包含模块标识。既有对象保留原身份，改名通过迁移预览完成。

例如，选择 inventory/default、类型“页面”、名称 Inventory，预览至少包含：

```text
新增 code/ui/InventoryPage.ts
新增 code/ui/InventoryPage.types.ts
新增 code/ui/generated/InventoryPageBinding.ts
新增 bundles/default/dynamic/ui/InventoryPage.prefab
修改 module.json 中的界面声明
更新该模块生成的 ViewKey、资源引用和资源索引
Creator 将为新增资源及目录生成对应 meta
```

实际面板展开后显示每一条真实相对路径，而不是仅显示上述概括行。复杂页面选择启用 Presenter 后，预览额外的 InventoryPagePresenter.ts；纯视觉 Prefab 可以不生成脚本。修改模板只影响后续新建对象，已有对象通过明确的重构操作迁移。

## 4. 统一资源目录，并明确打包边界

默认包与附加包同等处理，统一放在 bundles 下；default 表示默认选择，没有第二套存储或删除规则。

```text
assets/game/modules/inventory/
  module.json
  public.ts
  contracts/                   # 按需创建；公开类型及轻量值，不引用模块实现
  code/
    ui/
      generated/
    components/
    services/
    generated/
  bundles/
    default/                   # 配置为真正的 Creator Bundle
      dynamic/                 # 自动收录到框架动态资源清单
        ui/
        prefabs/
        icons/
        audio/
        config/                # 导出的配置数据
      static/                  # 同属此资源包，正常通过序列化引用使用
    extra/                     # 按需创建的另一个 Creator Bundle
      dynamic/
      static/
```

**实际 Bundle 根设在 `bundles/default`，附加包同样设在 `bundles/<包名>`。** dynamic 和 static 是同一资源包内的用途分类，不再单独配置为 Bundle。Bundle 根决定资源的组织与交付范围，dynamic 只决定哪些入口自动收录到框架命名访问清单；static 不进入这份框架清单，Creator 自身的构建元数据仍由引擎维护。

Bundle 名自动从模块和包标识推导。代码 Bundle 与各资源 Bundle 独立配置，不能把它们的父目录再次配置为 Bundle。运行时实际加载地址相对 Bundle 根计算，因此保留 dynamic 前缀，例如 `dynamic/icons/sword/spriteFrame`；框架逻辑名仍可为 `inventory/default/sprite/icons/sword`。

前一版将 dynamic 单独设为 Bundle，是为了让目录外的 static 素材按依赖收集、减少无引用素材导出；这不是静态资源自动进入主包的规则。目录外素材仅被某个 Bundle 的入口引用时会参与该 Bundle 的打包；同时被主包场景或其他 Bundle 引用时，需要结合优先级判断实际归属与重复情况。[Creator 的 Bundle 依赖和优先级规则](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)

本方案选择完整包目录，优先保持资源包边界清晰。代价是 static 中无引用的资源在默认导出规则下也可能被打包；先提供无引用资源报告，过滤或剔除优化须另行验证，不能承诺“不进框架动态清单就不会导出”。即便文件位于此 Bundle 内，跨包或主场景的静态引用仍可能影响最终归属，必须检查构建产物。

### 4.1 静态引用与实际归属

同包内部的静态引用正常使用。公共素材有明确的共享包归属；跨包静态引用需要声明为有意共享，并检查依赖链和优先级。主包启动场景、常驻预制体或主包资源直接引用按需包内容时，构建检查必须定位引用方，并阻止违反项目交付策略的引用。不能通过统一提高优先级来掩盖所有问题。

文件放入 static 不等于进入主包，放入 dynamic 也不保证按需下载。static 仍可能拥有 Creator 的加载地址；框架不生成其命名入口，也不把目录约定当成引擎访问限制。[Creator Bundle 归属与共享规则](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)

### 4.2 打包、下载与内存是三个不同范围

| 交付方式                   | 第一次访问一项资源时可能发生什么                                       | 拆小 Bundle 的主要影响                             |
| -------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------- |
| 普通远程资源文件           | 加载包元数据及代码，再请求目标资源和依赖；合并文件、图集会扩大请求范围 | 改变索引、合并与版本粒度；并非每项资源必然单独请求 |
| 远程 Zip 包                | 按目标平台适配下载、解压整个 Zip，再读取其中资源                       | 会改变首次下载字节与更新粒度                       |
| 小游戏平台本地分包         | 先由平台下载相应子包；进入包后再解析需要的资产                         | 会改变首次子包下载量、包数和平台限制占用           |
| 随安装包交付的原生本地资源 | 文件已随应用安装；按需读取、解析资源                                   | 主要影响组织、初始化和管理粒度，不等同减少安装量   |

本机 Creator 3.8.8 的 `platforms/minigame/common/engine/AssetManager.js` 中，Bundle 下载先调用 loadSubpackage；Zip 路径先执行 handleZip。因此“只加载一个资源”不能一概解释为“只下载这一个文件”。下载整包也不等于将全部资源解析为引擎对象或上传到 GPU。[Creator Bundle 加载与压缩模式](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)、[小游戏分包机制](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/subpackage.html)

对应“一关一包”和“所有关一个包”：内存中的目标关资源及依赖可以相近；冷启动下载量可能差很多，也可能差异很小，取决于上述交付方式和资源共享。不能默认每关拆包；应按共同使用频率、冷下载预算、更新频率及平台包数限制选择粒度。验收分别记录构建体积、冷/热缓存下载字节、加载后的内存和退出后的持有情况。

旧 res 通过 Creator 资产移动迁入 bundles/default，再在包内按用途整理到 dynamic/static；保留 UUID 后更新工具声明、地址与生成产物。不能仅修改文件夹文本路径或重建 Prefab。

## 5. 动态资源自动编目

采用目录约定：需要通过名字或类型引用加载的资源放 dynamic，只作为序列化依赖使用的资源放 static。移除逐个录入 UUID、类型和逻辑名的步骤。

编目读取 Creator 导入后的资源与子资源信息，不仅按扩展名猜测。支持的动态资产自动加入清单；meta、脚本、缓存、清单自身不参与递归编目。遇到不支持作为独立入口的文件，报告具体文件与处理方式，不能悄悄漏掉。图集纹理等依赖不会被错误登记为与图集帧相同的入口。

| 规则               | 具体处理                                                                |
| ------------------ | ----------------------------------------------------------------------- |
| 唯一身份           | 使用资产 UUID 和必要的子资源身份识别源资产                              |
| 完整逻辑名         | 保留模块、包、类型与逻辑名字，例如 inventory/default/sprite/icons/sword |
| 初始命名           | 首次从 dynamic 下相对路径自动生成                                       |
| 简称加载           | 在选定模块、包和类型内唯一时可用；重名返回候选项并报错                  |
| 类型安全           | 生成资源引用常量，业务优先使用代码补全；地址解析与实际加载分离          |
| 同包移动           | 工具维护并提交版本控制的 UUID→逻辑名映射，保留原逻辑名                  |
| 跨包/跨模块移动    | 作为重构操作预览并更新可解析引用；必要的旧名兼容显式记录                |
| 图片与图集         | 区分 ImageAsset、Texture2D、SpriteFrame；图集帧记录 atlas 与 frameName  |
| 删除或移出 dynamic | 检查配置、代码、UI 入口引用；报缺失，不自动删除使用方                   |
| 自动更新           | 资产导入完成后去抖更新；构建前做全量一致性检查                          |

稳定命名需要一份可重建地址、可追踪身份的版本化映射，但它由工具维护，开发者无需逐条登记。不能一边每次按新路径重新命名，一边承诺移动文件不会影响逻辑引用。

身份与生成物所有权记录放入可提交的工具数据目录，例如 `project-settings/generated/`，不能放在已被忽略的 .yzforge 中。源资产用 UUID/子资源身份；尚未导入的配置产物用稳定的表/分片身份，导入后再关联实际 UUID。删除留下失效记录，不把同名新 UUID 悄悄当成原资源；确认替换或明确重构后才能复用原身份。别名须无环、不遮蔽新名字，并列入兼容性检查。

### 5.1 逻辑名协议必须同步升级

重构前 catalog.ts 只接受四段 ID。当前已支持 `<module>/<bundle>/<kind>/<logicalPath...>`，前三段固定，逻辑路径至少一段。路径段统一规范化，禁止空段、`.`、`..` 和规范化后重名；原文件名不因生成逻辑名而被强制改名。

完整 ID 与命名空间内的相对名明确区分：scoped 字符串入口处理相对名，如 `load("icons/sword", "SpriteFrame")`；完整 ID 使用 `load({ id: "inventory/default/sprite/icons/sword", type: "SpriteFrame" })` 或生成引用。不能再用“是否包含 /”判断，因为相对名也可以有层级。旧完整字符串调用随迁移改为 AssetKey。

资源索引格式升级为 version 2，运行时解析、生成常量、UI 声明、配置 asset 字段、别名与检查器一次迁移；版本不支持时明确拒绝。旧四段 ID 可作为新语法的单段逻辑路径保留，既有业务引用不因自动扫描被无条件改名。

生成的运行时索引按资源包拆分，主包只保存必要路由；不能把所有包的完整清单或实际资产对象静态导入主包。配置导出的 JSON 通过本轮导出计划加入索引，上次生成结果不能被扫描后再次当作源数据。生成脚本和表内资源引用均与同一份目录校验。

生成顺序固定为：读取声明和源表 → 校验目标并规划配置输出 → 汇总真实源资产与计划产物 → 校验资源引用/表关联 → 写出发生变化的产物 → 等待 Creator 导入 → 解析真实地址并生成最终索引。工具自己的写入事件按本次操作合并处理，不能启动递归导表。共享枚举等产物按实际使用关系管理；删除一个来源不能误删仍被其他表使用的文件。只读检查发现产物不一致时失败，不替 CI 修改仓库。

dynamic/static 表达制作约定，并不改变引擎引用关系：Prefab 直接引用 dynamic 中的图片，图片仍可能随 Prefab 加载；从动态加载改为静态引用也不需要复制资源。框架不会因为有了清单而整包 loadDir。SpriteFrame 子资源和图集帧要按各自的真实加载方式处理。[Creator 动态资源与子资源加载说明](https://docs.cocos.com/creator/3.8/manual/zh/asset/dynamic-load-resources.html)

面板取消“登记动态资源”页面；检查结果仍可查看自动生成的名字、来源、重名、失效引用和实际包归属。

## 6. XLSX：工作簿配置页与选择器共用同一份规则

### 6.1 选择一种权威来源

建议采用 **工作簿内配置页作为唯一的表导出规则来源**。面板通过选择器编辑这份配置；目录仅用于整理工作簿，不再同时决定输出位置。这样工作簿移动或交给他人后，表定义和目标仍完整保留，也避免目录、外置 JSON、表内配置三套规则互相覆盖。

```text
Inventory.xlsx
  __config       # 默认放第一个；按固定 Sheet 名识别，不依赖排列顺序
  __enums        # 命名枚举定义，可选
  Items          # 数据表
  Prices         # 数据表
```

每个工作簿只属于一个模块，保证表与枚举归属明确。__config 包含带格式版本的约定区域：工作簿默认项、Sheet 导出项，以及按表标识关联的索引、约束和分片映射。导出项至少包含启用状态、Sheet、稳定表标识、目标资源包和主键；同一表标识对应哪些 Sheet 必须显式声明。

目标解析只有一条规则：工作簿默认包 → Sheet 覆盖 → 显式分片目标，均限定在所属模块；跨模块复用通过公共合同和表引用完成。面板读取工作簿后提供已有模块、资源包、Sheet 和字段选择，最后计算 JSON 和 TS 文件路径；不保存开发机绝对输出路径。引用不存在的目标、重复定义规则或存在未分配分片时导出失败。

工作簿内手动修改配置同样允许，导入时执行同样的存在性与类型检查。面板不能再维护一份长期独立生效的 tables.json；可以生成只读缓存来加快扫描，但缓存可随时重建。

“只改配置页”不能仅靠修改内存中的一个 Sheet 实现：将整个工作簿交给通用库重写，仍可能丢失未支持的内容。已有工作簿采用经验证的 OOXML 局部更新，保留其余 ZIP 条目及关联关系；优先创建完整配置模板，减少日后变更工作簿结构。ExcelJS 用于读取支持的数据和创建新模板，不默认保证任意工作簿无损往返。

写入前核对源摘要、备份，临时文件写完后重开校验，再替换源文件；校验无关条目、公式、格式及链接未被意外改动。被 Excel 占用、包含暂不支持保留的特性或版本已改变时，在覆盖前停止并指出原因。局部写入能力通过真实样本验收前，已有工作簿只能读取/手动编辑配置页，面板不能声称安全写回已完成。数据页由开发者在表格软件中编辑。

新建入口只生成 XLSX。已有 CSV 提供一次性转换预览，确认转换后的类型、数据和新路由一致后再移除旧映射；不能直接把后缀改为 xlsx。

### 6.2 类型、约束与枚举

保留直观的数据表表头：字段名、类型、默认值、注释；主键、索引、范围等通过配置区域和面板表格编辑。支持 int、float、bool、string、可空、一维数组、向量、颜色、明确格式的日期时间、表引用和类型化资源引用。字符串 ID、前导零、空值、零和 false 必须区别处理；超出安全整数范围的 ID 使用 string。

增加命名枚举，例如 __enums 中声明 ItemQuality 的 Common=1、Rare=2、Epic=3，字段类型可写：

```text
enum<ItemQuality>
enum<ItemQuality>[]
enum<ItemQuality>?
enum<common.ItemQuality>
```

默认从所属模块的枚举命名空间解析；同模块不同工作簿不得重复定义同名枚举。跨模块使用显式限定名和公开合同。枚举成员名、注释、存储值分开；存储值显式填写并保持稳定，数据单元格填写存储值，不能由当前行号产生或混合猜测成员名/值。重复定义、未知值、混合存储类型及生成标识冲突均在导出前报错。

生成独立的枚举常量与类型，例如：

```ts
export const ItemQuality = {
    Common: 1,
    Rare: 2,
    Epic: 3,
} as const;

export type ItemQuality = (typeof ItemQuality)[keyof typeof ItemQuality];
```

业务可使用 ItemQuality.Rare，字段得到相应类型与运行时合法值校验。默认不生成依赖跨文件内联的 const enum。注意常量对象也是运行时代码：仅类型使用时可以 import type，实际取值必须导入常量。跨模块公开的枚举、Row 类型与必要表描述生成到 `contracts/generated/`，与私有 code Bundle 分离；不得通过 public.ts 再导出 Service 或模块工厂。模块内部合同可保留在 code/generated。

工具区分合同引用、数据引用和运行时模块依赖；前两者本身不触发模块启动。共享枚举不需要加载其模块资源，但使用的常量代码会进入使用方的代码依赖。配置声明格式升级为 version 2；旧 `enum<a,b>` 是字面量列表，不能直接按新 `enum<Name>` 解析，尤其要避免把旧单成员枚举误判为类型名。迁移先生成具名定义并预览数据/合同差异。

### 6.3 联动与公式

跨表关联优先使用显式 ref<Table> 和导出期外键检查；运行时加载一张表不会因为外键自动下载所有关联表。公式用于制作数据，导出的 JSON 只包含计算结果。

当前 ExcelJS 能读取公式及缓存结果，**不能自行计算 Excel 公式**。[ExcelJS 公式说明](https://github.com/exceljs/exceljs/tree/v4.4.0#formula-value)

目标工作流区分两种状态：日常预览可读取 Excel 已保存的计算结果，并明确标记“使用缓存”；正式导出需要可验证的重算结果。缓存存在不能证明缓存最新。

需要公式的正式流水线应接入固定版本的重算工具，对工作簿副本及声明的关联输入进行计算、校验，然后导出。重算工具的函数兼容性需要单独验收；不能默认不同表格软件完全一致。CI 中无法重算时使用与源工作簿及依赖内容摘要匹配的已验证导出快照，或者明确失败，不能静默采用旧结果。

快照记录所有计算输入、配置规则、类型合同、导出器和重算器版本及计算设置的摘要；只匹配主工作簿文件名或修改时间不够。没有公式的工作簿直接校验导出，不要求安装重算器。面板修改目标或枚举也必须重新校验导出，不能沿用不匹配的旧快照。

工作簿内跨 Sheet 联动优先支持；跨工作簿公式需要声明参与计算的输入并纳入依赖快照。无缓存、公式错误、循环引用、结果类型不符都定位到工作簿/Sheet/单元格；生产数据对 NOW、RAND 等非确定性公式需要明确规则。首期不自研 Excel 公式引擎。

### 6.4 输出与运行时

导出 JSON 数据到所选包的 dynamic/config；生成对应 Row/Id/Indexes 类型、枚举及表合同，按前述公开/私有规则放置。服务端数据若后续需要独立导出，应另设目标，不能混入客户端 Bundle。

ConfigManager 保留 load、按主键查询、索引查询、遍历和释放等运行时入口；导表、公式重算属于编辑器/CLI。类型生成不能把整张表的数据作为 TS 常量编译进代码包。结构变更、枚举值变更、表版本与客户端兼容性都应进入导出差异报告。

外键的导出期完整性检查和运行时数据持有分开：检查可以读取声明的相关源表，不代表游戏自动加载它们；分片表查询必须先取得目标分片的加载句柄。跨资源包/跨模块数据引用不能被自动改写成 Service 初始化依赖，否则会破坏按需加载并产生初始化环。

## 7. 删除与恢复作为优先修复项

现有的“直接 fs.rename 整个目录，再刷新 asset-db”流程需要替换。API 返回成功与删除完成是两个不同事实；处理 EPERM 也不能只增加无条件重试。

切换到 Creator API 不能自动解除 Windows 文件占用。实施先用专门的测试模块复现，记录失败路径、系统错误、导入状态、编辑器请求结果和权限，再确定修复；不拿用户正在编辑的模块做破坏性试验，不在无证据时归因于某个进程。

目标操作流程如下：

1. 选中对象，生成真实文件与引用预览，包含 UUID、手写文件、生成文件和配置路由。区分真正外部引用与本次将一起更新的派生索引。
2. 检查相关 Prefab/场景编辑状态、未保存修改、进行中的导入与生成任务；任何需要处理的状态都给出具体对象。
3. 将完整恢复所需内容及 meta 备份到 assets 外的回收区，校验备份完整性，记录本次计划与操作阶段。
4. 通过 Creator 资产流程执行删除/移动；资源数据库与文件状态都确认成功后，更新声明和派生文件。恢复同样经过编辑器导入验证。
5. 逐步持久化完成记录。失败显示具体阶段和系统错误；恢复失败也单独记录，保留可恢复备份，不以通用“已完成”掩盖部分成功。
6. 再次查询数据库与磁盘，检查生成一致性后才标为完成。恢复验证 UUID、Prefab 脚本与字段引用，遇到新内容冲突不覆盖。

回收界面展示名称、类型、时间、状态和文件预览，点击恢复，不要求手填 restoreId。配置源工作簿属于独立制作资产；删模块时明确展示是保留工作簿并停用导出项，还是将它一并回收。保留时在 __config 中把受影响项设为 enabled=false；删资源包只影响对应 Sheet/分片目标。不能仅删除临时生成路由，否则下次扫描又会恢复导出，也不能另建长期生效的排除清单。

删除模块并保留源表时，停用工作簿级 enabled；扫描器仍列出原归属供恢复，但不对停用项要求模块存在，也不导出其枚举或数据。其他启用工作簿若引用其中的表或公开枚举，仍阻止删除。删包只停用相关目标，不能连带关闭仍有效的其他 Sheet。

工作簿修改纳入同一预览、摘要检查和备份；文件占用导致不能安全写回时，删除在变更前停止。恢复时检查目标和源摘要后恢复启用配置。Creator 操作与工作簿写入不具备跨系统原子提交，使用分阶段记录和补偿恢复；部分失败必须显示实际状态，不能承诺“任何失败都像从未执行”。

引用阻止删除时可以定位使用方。框架自动生成的注册项随删除计划更新；业务代码的显式引用需要开发者处理。运行时拼接字符串无法完整静态证明，工具应报告检查边界。

已验证纯代码模块、默认资源包单独删除恢复、带 UI/Part/配置的整模块删除恢复，并逐项核验 41 个资产与目录 UUID、节点绑定和工作簿设置。删除中途失败有备份与阶段记录；进程崩溃、系统重启等更广泛故障场景尚未完整验收，不能由一次成功恢复推导。

## 8. 普通预制体和自动绑定

将编辑器中的节点扫描、字段生成、序列化引用写入抽成同一套绑定能力，并生成适配不同角色的模板：

| 对象                     | 运行时职责                                          |
| ------------------------ | --------------------------------------------------- |
| 页面/弹窗等 UIView       | UIManager 管理显示、隐藏、导航、参数和结果          |
| ItemPart 等 UI 子组件    | 父界面管理其数据、事件和显示期限，不进入页面栈      |
| CoinComponent 等普通组件 | 处理普通节点行为，由所属模块/实例提供生命周期上下文 |
| 纯视觉 Prefab            | 无业务脚本也可使用，不强迫生成空类                  |

已有或手动制作的 Prefab 提供“接入自动绑定”：选中真实资源 → 选择角色和脚本 → 预览生成字段与将挂载的组件 → 生成 Binding → Creator 写入引用 → 读回验证。不能覆盖现有手写脚本；已有继承关系不兼容时给出明确的代码改造预览。

绑定范围以当前组件/Prefab 为边界。嵌套 Prefab 自己管理内部绑定，外层可以持有其组件；不能越界重写嵌套资产。重复节点名字、缺组件、过期绑定均可定位。保存 Prefab 后可去抖更新绑定，生成文件引起的导入事件不应造成循环生成。

现有 `Assets.instantiate → App.bindInstance` 已负责普通 Prefab 的 Scope、GameComponent 上下文注入和激活许可，activate 也已有后续启用入口。此前判断“主要依赖 UIManager”不准确。本轮复用并扩展这条链路，不另建 PrefabManager。

ItemPart 使用适配 GameComponent 的生成 Binding，并受父界面显示 Scope 约束；Part 是职责后缀，不因此新增一套独立 UI 管理器或生命周期体系。

扩展时分清三种身份：资产属于哪个资源包、反序列化需要哪些代码模块、实例由哪个业务上下文管理。资源在 common 包，不代表其中的 ItemPart 应被注入 common 的业务上下文。目标索引以 `requiredCodeModules` 表达包含嵌套 Prefab 在内的脚本依赖，替代把所有情况压进单个 codeModule；引擎及已在主包的共享脚本无需伪装成业务模块。

加载方先保证必需代码注册，创建未激活实例，再通过受管入口显式传入或继承父宿主的业务上下文并校验绑定，最后允许业务激活。跨模块使用服务时显式取得并持有模块句柄；不能猜测资源目录后自动启动模块。模块工厂可以准备自身的未激活实例，不能在初始化中等待自己 moduleReady。共享 Part 优先接受数据和回调，减少模块上下文依赖。

场景中手动放置的组件通过 `app.bindScene(root, moduleId, owner)` 接入宿主。GameComponent 已记录引擎与注入就绪状态，在两者满足后才进入业务钩子；业务不调用私有 __bind。资源创建入口显式携带调用方上下文，已验证跨模块动态 Part 使用父界面的宿主。

对象池属于按需增加的能力。启用时必须额外区分实例生命周期与每次复用生命周期，避免列表格子复用后旧图片请求覆盖新数据。业务仍只使用框架钩子，不覆盖引擎 onLoad/onEnable/update 等入口。

## 9. 代码配置与资源配置

在 **Creator 项目设置 → Bundle 配置** 中建立两份可复用的项目配置方案：

| 配置             | 绑定对象                         | 默认策略                                           |
| ---------------- | -------------------------------- | -------------------------------------------------- |
| YZForge 代码配置 | 实际进行代码分包的模块代码目录   | 已适配的小游戏采用本地分包；启动所需代码保留主包   |
| YZForge 资源配置 | 各资源包的 bundles/<包名> 根目录 | 已适配的小游戏默认本地分包；Web/原生按项目交付选择 |

这是两份真实的 Creator Bundle 预设，模块引用预设 ID；工作台读取并展示其生效结果，开发者修改预设可统一影响使用方。不能仅在框架 JSON 中增加两个字段，同时让 Creator 继续使用平台默认配置。Creator 本身支持在项目设置中自定义 Bundle 配置方案。[Creator Bundle 配置](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)

普通模块默认继承项目策略，确需例外时明确显示例外及原因；框架不另存一套可能与 Creator 冲突的压缩/远程配置。构建根据实际目标平台读取生效配置，避免手动 activePlatform 与真实构建目标不一致。

“小游戏统一分包”适用于已验证支持分包的目标及可拆分内容。引擎、启动引导和加载分包所需代码必须可首先执行；不同小游戏平台的能力与限制需要独立适配。**小游戏本地分包与远程资源包不能在同一个包上同时启用**，切换为远程资源时应让互斥关系在面板和后端都生效。[Creator 小游戏分包说明](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/subpackage.html)

代码分包还需要数据化入口、加载后注册与明确依赖顺序。主包只引用必要合同和轻量标识，避免静态 import 模块实现；Prefab 反序列化前保证所属组件类已注册。脚本跨包引用及远程代码的目标平台行为要用真实产物验证。[Creator Bundle 脚本说明](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html#asset-bundle-%E4%B8%AD%E7%9A%84%E8%84%9A%E6%9C%AC)

generate.mjs 已将代码 Bundle 的本地交付记录与入口纳入 release.bundles，资源包仍禁止业务脚本。构建后检查真实产物中的 Bundle 和代码入口归属；本轮 Web 运行验证了按需请求代码、重复打开复用代码注册，微信构建也输出独立代码与资源分包。已移除未验证的 bundledVerified 开关，平台完成范围以实施记录为准。

优先复用已有 `code/entry.prefab` 引导机制：该小型入口只负责取得工厂，不静态引用业务资源。eager/bundled 决定实现代码是否进入独立 Bundle；Creator 预设决定这个 Bundle 在平台上如何交付，两个维度不能互相替代。私有 code 的跨 Bundle 静态 import 应被阻止，共享依赖通过框架或公开 contracts 解决。

模块关闭会清理业务 Scope 和资源持有，不保证卸载已执行的 JS 或撤销 ccclass 注册；同一运行会话的代码版本保持固定。远程资源内容可以按兼容规则更新，不因此引入远程代码插件安装体系。

两个预设建立完成不等于代码分包交付完成。验收需检查构建代码归属、平台分包配置、首包体积和运行时第一次进入模块的加载记录，保留当前未验证状态直到取得证据。

## 10. 页面逻辑：View + 可选 Presenter + Service

当前 Dashboard 示例包含渲染、读表和按钮流程，可用于演示 API，但不应成为复杂业务页面的唯一模板。

推荐的职责如下：

| 文件                              | 负责                                       | 不应承担                               |
| --------------------------------- | ------------------------------------------ | -------------------------------------- |
| InventoryPageBinding.ts           | 自动生成节点/组件引用与校验                | 业务逻辑、数据请求                     |
| InventoryPage.ts                  | 显示数据、节点交互、动画、转发用户意图     | 背包规则、持久化与共享业务状态         |
| InventoryPagePresenter.ts（按需） | 页面用例、加载状态、调用服务、组合显示数据 | 持有引擎节点、拥有跨页面的权威业务状态 |
| InventoryService.ts               | 业务规则、共享状态、业务操作及其结果       | 操作 Label/Button、寻找其他页面节点    |

Presenter 使用普通 TypeScript 类与窄的视图接口，通过构造函数获得依赖。每次页面显示持有自己的作用域，隐藏时取消显示任务与订阅；页面缓存不延长旧任务。Service 由模块管理，在多个界面之间共享其业务状态。已经提交的业务操作与界面是否继续显示分开处理。

简单 Toast、纯确认弹窗可以直接由 View 调用服务并渲染，不强制生成 Presenter、Model、Controller、Repository 等一整套空文件。模板按复杂度选择，后续也可以提取 Presenter。

组件之间用数据与回调，弹窗与调用方用参数/结果，跨模块命令与查询用类型化公开 API，共享事实变化用有范围、可清理的事件订阅。禁止为了通信遍历其他页面节点、保存其他 View 单例，或让所有交互都依赖字符串全局事件。

## 11. 额外需要一起解决的问题

| 问题                             | 处理要求                                                          |
| -------------------------------- | ----------------------------------------------------------------- |
| 创建中途编译失败留下半套文件     | 执行计划、操作记录、只回滚本次拥有的产物；重试不覆盖用户内容      |
| 保存时生成/导表与 CLI 同时运行   | 面板与 CLI 共用项目锁、输入摘要和稳定输出排序                     |
| 自动扫描造成全量重写或无限循环   | 导入完成后再扫描，区分源输入与生成物，内容不变不写文件            |
| 引擎编辑器版本变化影响绑定       | 核对序列化接口与编译后的属性集合，版本不支持时明确失败            |
| 移动、重命名后引用损坏           | UUID、逻辑 ID、类名、路径分开处理；跨对象重构统一预览             |
| 新机器无法识别旧生成物           | 所有权和稳定身份信息进入版本控制；本地 .yzforge 只作缓存/恢复记录 |
| 静态引用提前拉入资源或重复打包   | 构建报告包含依赖链、真实包归属与重复资源                          |
| 配置/远程资源与客户端不兼容      | 导出与发布记录结构版本、内容摘要及兼容范围                        |
| UI 关闭或格子复用后异步回写      | 每次显示/复用隔离任务，迟到结果禁止修改新的界面状态               |
| 面板输入约束与直接脚本调用不一致 | 两者调用同一套规则，保存前验证完整关系                            |

## 12. 实施顺序与验收

| 顺序                   | 可独立验收的结果                                                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------------------- |
| P0：验证边界与可靠操作 | 小样验证两类 Creator 预设、代码 Bundle 交付与公开合同边界；复现并修复删除/恢复，全文件预览与后端校验一致 |
| P1：日常制作流程       | 联动选择、后缀与角色 ID、已验证的统一 Bundle 目录、通用 Prefab/绑定和实例/场景生命周期                   |
| P2：资源与配置         | 资源协议迁移、dynamic 自动编目、稳定身份、XLSX 安全写入/目标选择、命名枚举、公式与快照流程               |
| P3：整体交付验收       | View/Presenter/Service 示例、旧项目迁移、完整构建依赖报告及各目标平台实际下载/运行验证                   |

这些是实现顺序，不是删减范围。迁移前先输出旧新目录、逻辑 ID、路由、预设和生成产物的完整差异；经 Creator 保留 UUID 移动资产，再重新生成绑定与目录，并完成代码、预览及构建验证。

最终应让新开发者完成以下链路：选择模块和名字创建页面 → 预览文件 → 编辑节点并自动绑定 → 创建并复用道具组件 → 将图片放入 dynamic 后直接使用生成引用 → 选择 XLSX 导出包、使用命名枚举和公式结果 → 切换项目分包预设 → 删除无引用模块并完整恢复。过程中不需要手填 UUID、路径、恢复 ID 或索引 JSON。

## 13. 本轮复审结论与必要验收

目录方向保留：`bundles/<name>` 才是 Bundle，dynamic/static 仅区分框架命名入口与依赖素材。前版尚不足以直接实施，以下缺口已在文档中修正，运行时及工具修复仍待完成。

| 级别 | 发现                                                   | 必须取得的实施证据                                                   |
| ---- | ------------------------------------------------------ | -------------------------------------------------------------------- |
| 阻断 | 多级资源名与现有四段解析器不兼容                       | 新旧 ID 迁移、相对路径、同名/子资源、别名及版本拒绝验证一致          |
| 阻断 | 代码 Bundle 交付记录缺失，公共常量可能穿透私有代码边界 | 主包不含私有实现，首次加载代码入口成功，共享枚举可用且不启动业务模块 |
| 阻断 | 工作簿写回安全性与公式新鲜度不能靠普通读写保证         | 无关 OOXML 内容保留、锁/并发失败不损坏文件、公式快照失效检查通过     |
| 高   | 删除流程未解决真实错误，也未覆盖表内权威配置           | 专用样本复现；阶段故障、停用导出、重启恢复和 UUID 保留通过           |
| 高   | 资产归属、代码依赖、业务宿主被混为一个模块             | 共享包 Prefab、嵌套组件、未激活实例和场景手放组件均按正确顺序初始化  |
| 高   | “单资源加载”等同“单文件下载”的说法不成立               | 对普通文件/Zip/小游戏分包分别记录冷下载、依赖与内存，标明平台和配置  |
| 高   | 文件后缀区分了角色，旧 views ID 仍可能冲突             | 同名 Page/Popup/Part 可共存；迁移不改变旧身份                        |
| 中   | 自动生成缺少稳定身份、所有权和确定顺序                 | 清缓存重建、源资产移动、配置新增/删除、重复导出不产生失效或无限循环  |

不额外引入 Extension、ContentPack、PrefabManager 或通用事务容器。本轮补充的是现有机制的必要边界和验证条件；证据齐备后才在实施记录中标记交付。
